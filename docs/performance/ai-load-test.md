# AI 동시성 부하 실험

동시 요청이 늘어날 때 FeatherlessAI 세마포어 permit 4가 처리량과 지연에 어떤 영향을 주는지 측정했다. 트래픽을 크게 넣는 것이 목적이 아니라, 같은 조건으로 다시 돌릴 수 있는 통제 실험이다.

실제 외부 API는 호출하지 않았다. 목 Provider 지연은 500ms, 동시 처리 한도는 4다. 세마포어 최대 permit도 4로 두었고 제거하거나 단순화하지 않았다. 획득 타임아웃은 Planning Agent와 같이 10초다.

## 실험 방법

k6가 닫힌 워크로드로 동시성 1, 2, 4, 8, 16, 32를 각 20초씩 반복한다. 각 VU는 `POST /internal/ai-loadtest/call`을 루프한다. 이 경로는 운영 앱이 아니라 부하 실험 하니스다. 하니스는 운영 코드인 `FeatherlessAiRateLimiter`로 Redis 세마포어를 잡고, 잡은 뒤에만 목 Provider를 호출한다. 호출이 끝나면 permit을 반드시 반환한다. 획득에 실패하면 503을 주고 목 Provider는 호출하지 않는다.

다시 실행하려면 k6와 Docker가 있는 환경에서 `observability/loadtest/run.sh`를 실행한다. 스크립트는 Redis와 하니스를 띄우고 외부 API 주소는 쓰지 않는다. 기본 PR CI는 이 스크립트를 돌리지 않는다. CI는 Redis Testcontainers 위에서 세마포어가 목 Provider 동시성을 4로 막는지 확인한다.

측정 시각은 2026-09-10이다.

## 결과

사용자 지연은 k6 `http_req_duration`이다. Provider p95와 세마포어 대기 p95는 하니스를 스크레이프한 Prometheus 히스토그램이다. 오류율은 획득 타임아웃과 목 Provider 한도 초과만 포함한다.

동시성 1의 p99 1730ms는 표본 37개 안의 꼬리다. 포화 판단에는 쓰지 않는다. 동시성 4의 p95 1112ms는 한도에 딱 맞을 때 생기는 짧은 경합이다. 대기 p95는 1ms로 남았고 Provider p95는 532ms로 그대로다.

목 Provider가 관측한 최대 동시 호출은 동시성 1에서 1, 2에서 2, 4 이상에서 4다. 한도 초과 응답은 한 번도 없었다.

## 해석

### 포화는 어느 동시성부터인가

permit 4와 목 한도 4가 같아, 동시성 4에서 세마포어가 가득 찬다. 동시성 8부터 대기 p95가 500ms대로 올라간다. 그 지점부터 포화로 본다.

### 처리량은 어디서 멈추는가

이론 상한은 4 permit을 500ms마다 비울 때 초당 8건이다. 측정값은 동시성 4에서 6.74, 8에서 7.31, 16에서 7.96, 32에서 7.50이다. 동시성을 4 너머로 늘려도 처리량은 약 8 RPS에서 멈춘다. 요청을 더 넣는 만큼 처리량이 늘지 않고 대기 줄만 길어진다.

### 대기 지연은 언제 급증하는가

동시성 1~4에서 대기 p95는 2ms 이하다. 동시성 8에서 537ms, 16에서 3.5초, 32에서 7.1초다. 대기 줄 길이는 대략 `동시성 - 4`에 비례한다. Little의 법칙으로 보면 처리량 8 RPS에 동시성 32면 체류 시간은 약 4초 중앙값이고, 측정 p50 3512ms와 맞는다.

### 세마포어가 Provider를 보호하는가

보호한다. Provider p95는 모든 동시성에서 532ms로 목 지연과 같다. 목 한도 초과는 0건이다. 동시성 32에서도 목 쪽 최대 동시 호출은 4를 넘지 않았다. 남는 요청은 Provider를 두드리지 못하고 세마포어에서 기다린다.

### 사용자 체감 지연은 어디서 나빠지는가

동시성 8부터 체감이 나빠진다. p50이 544ms에서 1004ms로 늘고, 16에서 1.5초, 32에서 3.5초다. p95는 16에서 4초, 32에서 8초다. 늘는 쪽은 Provider가 아니라 세마포어 대기다. Planning Agent 획득 타임아웃 10초에 맞추면 동시성 32에서 타임아웃 3건이 나왔다. 추출 경로의 획득 타임아웃은 60초라서, 같은 부하에서는 실패 대신 더 긴 대기가 될 수 있다.

## 알림 임계값

`AIProviderHighLatency`는 60초를 유지한다. 이 실험의 사용자 p95 약 8초는 목 지연 500ms에 대기 큐를 더한 값이다. 운영 FeatherlessAI 호출 지연은 500ms가 아니다. 운영 실측이 있기 전에는 호출이 멈춘 수준만 알린다.

세마포어 포화 알림은 남은 permit이 1분 동안 0일 때다. 이 실험에서 동시성 8 이상은 20초 동안 포화가 유지되었다. 순간 포화와 지속 포화를 나누는 기준은 그대로 둔다.

## CI

기본 PR CI는 k6를 실행하지 않고 실제 외부 API도 호출하지 않는다. `AiConcurrencySaturationTest`가 Redis 위에서 세마포어가 목 Provider 동시성을 4로 제한하는지 확인한다.
